# 要約パネルの気温の表示元

2026-11-27。設定 → AMeDAS →「要約パネルの気温」で、次を選べる。

- 最寄り観測点の実測値：従来の現在地付近のAMeDAS表示。
- MeteoScope独自推定：既存の標高・環境・平年差補正の計算を変更せずに使用。従来どおりアーリーアクセスと利用規約への同意が必要。
- 気象庁の推計気象分布：現在地を含む約1km格子の気温区分。アーリーアクセス認証を必要としない。

湿度・降水量・風などと、選択観測点の観測グラフ・ランキングは従来どおり。独自推定に気象庁の推計分布を入力しない。既存の独自推定ON設定を初回移行時に引き継ぎ、それ以外は最寄り実測が初期値。新しい選択は端末内に保存する。アーリーアクセス失効中の独自推定は実測表示となり、設定内の独自推定は選択不可となる。

## 気象庁からの取得

公式ページで使用する、無料で公開されている次のデータをブラウザから直接取得する。実レスポンスでJSON・PNG・CORSを確認した。

- `https://www.jma.go.jp/bosai/jmatile/data/suikeikishou/targetTimes.json`
- `https://www.jma.go.jp/bosai/jmatile/data/suikeikishou/{basetime}/none/{validtime}/surf/temp/10/{x}/{y}.png`
- [公式ページ](https://www.jma.go.jp/bosai/suikei/#elem=temp)
- [公式ページの表示定義](https://www.jma.go.jp/bosai/suikei/table/suikei.properties__9daf0e6a65268e2c351d.xml)
- [製品の仕様](https://www.data.jma.go.jp/suishin/shiyou/pdf/no13801)

通常の表示用PNGは、拡大時でも1℃区分。今回、GRIB2の0.5℃の原数値を取得したとは扱わない。色区分をそのまま「10〜11℃」と表示する（下端を含み上端は含まない）。中央値10.5℃を実際の推計値のように表示しない。最低・最高端は「−29℃未満」「44℃以上」。未知の色・透明・半透明・欠測は取得不可とする。近くの数値ラベルや別格子から値を借用しない。

元画像は独自に加工して表示区分を読み取る。ダーク／ライト用に色を変換した画像ではなく、公式の元PNGを読み取る。約1km格子の中心をサンプリングし、格子境界付近で隣の色を取得するリスクを抑える。JMAの512px画像タイルの座標は、z=10で通常XYZの半分のスケールとなることを実データと照合した。

## 時刻の扱い

AMeDASの14桁時刻はJSTだが、こちらの`basetime`と`validtime`はUTC。別の厳格なパーサーを使い、日付の桁や実在日付も照合する。既存のAMeDAS時刻変換へ渡さない。

- カタログに掲載され、`temp`を含み、`basetime === validtime`の実況だけを使用する。
- 未来時刻は使わない。現在以前で最新の掲載時刻を選ぶ。
- 最大90分前までとする。現行の毎時更新・公開遅延を考慮した運用上の上限であり、精度保証ではない。
- 取得後も古さを再確認する。再描画でも期限を確認し、期限切れの区分は消す。
- 詳細に対象時刻と取得時刻を別々に、日本時間の月日・時分で表示する。
- 正時直後に前時刻のデータを使う場合も、その実際の対象時刻を表示する。現在時刻やAMeDASの観測時刻へ付け替えない。
- 最新格子が欠測・取得失敗なら「—」。前の時刻や最寄り実測へ黙って切り替えない。

実通信確認では`20261126160000`を`2026-11-26T16:00:00Z`と解釈し、「11/27 01:00」と表示した。取得時刻「11/27 01:33」と区別した。公開検証地点のみを使用し、ユーザーのGPSを取得・送信していない。

## 負荷とプライバシー

時刻一覧は既存の共有JSON取得処理で60秒キャッシュ。要約パネルの通常更新（既存の5分更新等）に合わせて確認し、地図移動のたびには取得しない。PNGは同時取得をまとめ、最新4タイルまでメモリに保持する。失敗後は60秒間、再描画による連続リトライを抑える。位置は含まれる格子が変わったときに読み直す。同一タイル内なら画像を再利用する。

新しいサーバー処理・D1・DO・定期実行・有料APIは追加していない。位置が固定されていれば通常、時刻一覧は約12回/時、PNGは新しい対象時刻ごとに約1回/時。実際にはAMeDAS画面の表示状況・操作・移動による。気象庁へ送るのは周辺タイル番号で、緯度・経度そのものを送るクエリは作らない。タイル番号からおおまかな地域は分かる。

## 構成と確認

- `src/preferences/temperatureSource.js`：3択の永続化、旧設定移行、同意待ち中の切替の整合性。
- `src/jma/estimatedTemperature.js`：公式時刻、タイル位置、区分の読取りと少数キャッシュ。
- `src/location/jmaTemperatureController.js`：読み込み、期限、遅延応答の破棄、失敗時の連続取得抑制。
- 設定・要約・詳細は既存のUIを共用。PNG画素読取りも標高取得と共通化し、標高の数値デコード・独自推定アルゴリズムは変更していない。
- `Tests/JmaTemperatureDisplayTests.mjs`：UTC/JSTの日付またぎ、未来・期限切れ、欠測、キャッシュ、遅延応答、設定移行・同意競合・表示を検証。
- `Tests/browser/jma-temperature.html`：公開地点でブラウザの実PNG・CORS・最新時刻を確認する検証専用ページ。製品ビルドには含めない。

ブラウザでは設定の3択と選択状態、公開地点の実データ取得、対象時刻、欠測、390px幅のライト表示、横にはみ出さないことを確認した。全189テストスイートとビルドが成功した。iOS向けも同じWeb/PWA実装を使用するが、iPhone実機・ネイティブビルドの証拠ではない。実装・検証段階ではコミット・push・デプロイせず、その後ユーザーのリリース指示を受けた。

将来、公式表示の色・座標・時刻形式が変わった際は更新が必要。原数値が必要な場合はGRIB2等の無料かつ持続可能な取得経路を別途確認する。この実装は気象庁の実況推計製品を表示するもので、独自の将来予報ではない。ただし製品自体には気象庁がLFM等を利用していることを詳細に明記した。
