# 推定気温：風・地形・観測履歴の比較（2026-11-26）

## 結果と不採用の判断

数値予報は使用しない。既存の標高・環境補正付きIDWへ、周辺の風向が過去観測でも持続している場合の環境・風向の類似度を追加する候補を比較した。しかし誤差の大きい側で悪化が残るため、今回は新しい補正の採用を見送った。`weatherEnabled: false` にして通常のアプリは既存の計算方式を維持する。比較・再現用のコードだけを残す。

候補の改善は非常に小さい。未使用時刻の全出力MAEは1.2102223→1.2093183℃、差は約0.0009℃だが、補間対象の95%点と一部時刻のRMSEが悪化した。平均の小さな改善だけでは採用しない。既存の推定気温のアーリーアクセス限定・初期OFFの設定と、有効化規約は維持する。

## 比較した3種類の条件

1. 弱風・夜間・地形・直近の冷却傾向が重なる場合の標高補正の減衰。これは改善せず不採用。続いて標高補正値は変えず、近い標高の観測点の重みを増す方法も比較したが、単独採用より良くならなかった。
2. 風向・風速と、土地被覆・海面割合・地形の類似度の組み合わせ。地域の風向が過去にも持続する場合だけ、異なる風向・環境を持つ観測点の寄与率を抑える。平均誤差では最良だったが、大きな誤差や時刻別の悪化を理由に不採用。海風や山越えの風を直接検出したという主張はしない。
3. 30分間の気温変化の違いによる重み付け。周辺の変化の加重中央値から離れる観測点を軽くする方法を試したが、改善せず不採用。過去の値を現在値として混ぜたり、将来へ外挿する方式ではない。

2系列でそれぞれ27組の係数を比較した。最終系列は、夜間強度0/0.5/1、風強度0/0.25/0.5、気温変化強度0/0.5/1。平均誤差による評価候補は風強度0.5、夜間・気温変化強度0だった。夜間・気温変化の候補は `scripts/temperatureWeatherCandidates.mjs` に分離しアプリへ配信しない。風候補もアプリでは無効とした。

## 検証した風・地形候補のアルゴリズム（アプリでは無効）

既存の観測品質・時刻・鮮度・水域経路・標高外挿のフィルターと観測点選抜を維持する。選抜した最大8地点の既存重みを使い、風向を円周ベクトルへ変換して平均する。北付近の359度と1度を南へ平均するような演算はしない。風向は気象庁定義の「吹いてくる方向」として扱う。

現在と20～60分前の観測に、それぞれ有効な風が3地点以上・重みの70%以上あり、平均風速2m/s以上・ベクトル整合度0.7以上の場合に限る。履歴は30分前に最も近い時刻を選ぶ。現在と過去の平均風向の内積が正である場合、その持続性と観測点ごとの風向差・環境差に応じて元の重みに係数を掛け、最後に正規化する。係数は0.5～1に制限する。

欠測・品質不良の風は既存の `buildAmedasPoints` のフィルターを共有する。静穏・無効な風向を北として扱わない。環境・標高がない場合、弱風・風向が不揃い・変化した場合、履歴がない場合は新しい調整をせず従来方式を維持する。固定気温減率0.0065℃/m、動的減率OFF、重み更新後のばらつき・フォールバック判定は維持する。confidenceを風だけで引き上げない。

## 検証設計

作業開始時の未コミット修正を含む気温エンジンを `.cache/temperature-weather-study/baseline/` へ保存し、ハッシュを記録した。以前の個人位置情報・アプリ比較値は使用していない。公開全国観測のみ。

- 調整用：既存の2026-11-25 19:40～11-26 18:10 JSTの9時刻、延べ8,231対象。各時刻の30分前の公開全国観測を追加取得した。
- 係数固定：2026-11-26 12:39:24 UTC。選択記録は `.cache/temperature-weather-study/selection-weather-v2.json`。
- 評価用：係数固定後に初めて取得した11-26 19:00・20:00・21:00 JSTの3時刻と、それぞれ30分前の観測。延べ2,747対象。
- 対象観測点を現在の温度・風・過去の観測のすべてから除外するLOO。対象地点の標高は観測点表から与え、推定に対象の実測温度は渡さない。
- 調整時は既存採用点の寄与率を比較し、評価時はフォールバックを含む実際のアプリのエンジンを実行した。
- 選択基準：MAEとRMSEの低下、既存補間対象の最大絶対誤差を増やさない、各時刻のMAE悪化が0.03℃以下。その中で調整用MAEが最小の係数を選び、評価用データでは係数を変更していない。
- 上は当初の比較候補の選択基準であり、採用基準として不十分だった。ユーザーの指摘を受け、全出力・同一補間対象のMAE、RMSE、95%点、最大絶対誤差と、各時刻のMAE・RMSEが悪化しない条件に見直した。調整用27候補に、この条件を満たしてMAEも下げるものは0だった。既知の評価時刻へ再調整して採用することはしない。
- 非採用ロジックを検証専用へ分離し、履歴の対象地点を物理的に削除した後も、評価3時刻の全予測の数値差は0だった。

## 実装・通信・UI

- `temperatureWeather.js` は比較・再現用の無効な候補。明示的に検証用の `weatherEnabled: true` を与えた場合だけ風補正を実行する。通常のコントローラーは履歴を蓄積せず、風補正を行わない。
- 候補の設計は受信済み全国観測を最大10時刻・90分、メモリ内だけに保持し、20～60分前の履歴を使うもの。検証は30分前の履歴がある状態だった。過去データの取り寄せ、端末保存、現在地のサーバー送信は追加していない。
- 追加のAPI・D1・Durable Objects・定期ジョブ・数値予報・有料サービスはない。Cloudflareへの追加リクエストは0。開発時の検証データ取得は端末運用には追加していない。
- `temperatureObservation.js` の時刻変換、既存の距離・環境差・観測値品質フィルターを共有し、重複実装を避けた。
- 風候補を明示的に有効化した検証画面では、その調整と参照した過去時刻を確認できる。通常の画面には風補正の説明を追加表示しない。要約はユーザーの追加指示に合わせ気温と単位だけを表示し、標準のAMeDAS観測値と同じ字体・太さを共有する。推定・参考・更新中の区別は詳細と読み上げ用の名前に保持する。

## 確認と再現

風の円周平均、逆風・弱風・無効値、欠測、時刻不一致、未来・古い履歴、重みの上限、実測への切替、対象地点の履歴除外、履歴の上限・OFF消去、再描画時のI/O抑制、詳細表示を自動検査した。

既存の公開観測キャッシュと基準コードの保存が必要。クリーンなcloneに原データは含めない。

```powershell
node scripts/validate-temperature-weather.mjs --replay
node scripts/validate-temperature-weather.mjs --evaluate
node --test Tests/TemperatureWeatherTests.mjs Tests/LocalTemperatureControllerTests.mjs
npm.cmd test
npm.cmd run build
```

共通Web/PWAコードを更新した。実iPhoneのGPS・Safari、ネイティブiOS、GitHub CI、本番配信の確認ではない。ユーザーの指示に従い、コミット・push・デプロイは実行しない。

最終確認：全体186スイート成功。風候補を無効化した後の関連42テスト成功。日本語・ダーク430×932と英語・ライト320×568で14項目のブラウザー回帰チェックが成功し、要約の可視文字が気温だけであること、標準観測値とフォント名・12px・太さ900・数字幅の指定が一致すること、横あふれがないことを確認した。最終ビルド成功（266モジュール、既存の大きいチャンクの警告あり）。差分の空白検査成功。

不採用後の既存方式との一致検証は公開全国観測12時刻・延べ10,978対象で実行した。温度差0℃、出力種別・観測点の寄与率・注意フラグもすべて一致した。記録は `.cache/temperature-weather-study/baseline-parity.json` と集計JSONの `verification`。計算方式を改善したという報告ではなく、今回の風候補による悪化をアプリへ反映していないことの確認である。
