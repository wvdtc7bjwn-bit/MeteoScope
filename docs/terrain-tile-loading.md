# 地形タイルの取得と再利用

## 対象と変更

国土地理院の色別標高図 `relief` と陰影起伏図 `hillshademap` のみに適用する。
雨雲、警報、地震などの更新データは、このキャッシュに入れない。

従来はMapLibreの画面サイズに応じたタイルキャッシュとブラウザーのHTTPキャッシュに依存していた。
近距離の往復では通信しないが、広域を移動してタイルが退避された後は、同じ画像の取得とデコードが再発していた。

`src/map/terrainTiles.js` の専用プロトコルで、国土地理院から取得したPNGのバイト列を再利用する。

- メモリー：LRU、最大8MiB。
- Cache Storage：画像本文の合計最大32MiBかつ512件。古い保存項目から削除する。
- 保存待ちのデータ：最大8MiB。1画像512KiBを超えるものは表示するが保存しない。
- 有効期限：最大24時間。配信元の `max-age` / `Expires` が短ければそれを優先し、`no-store` / `no-cache` は保存しない。
- 保存領域を使えない場合は通常取得へフォールバックする。保存の完了は描画を待たせない。
- 同一画像の同時要求は共有し、全要求が中止された時点で通信を中止する。失敗・404・PNG以外の応答は保存せず、次回取得を妨げない。
- 描画側へは別のArrayBufferを渡し、ワーカーへの転送で保存済みバッファーが切り離される問題を防ぐ。

画像の再圧縮、再サンプリング、解像度低下は行わない。MapLibreの全ソース共通のGPUキャッシュ上限も変更しない。
色・濃さ・警報などとの重なり順と、地形OFF時に新規取得しない動作を維持する。
サーバー側の画像保存やD1の利用は追加していない。

## 縮小時に消える問題

[国土地理院のタイル一覧](https://maps.gsi.go.jp/development/ichiran.html)では、色別標高図はズーム5～15の提供。
MapLibreの通常の256pxラスターレベル選択では、地図ズーム3.5未満でズーム4を要求する条件になり、ソースの最小ズーム5を下回って表示されなかった。

地図ズーム3～3.5未満には広域表示用ソースを使用し、既存のズーム5 PNGをそのまま表示する。
`tileSize: 128` はMapLibreの取得レベル選択に用いる値で、実画像は元の256pxのまま。
広域ソースの取得を日本の範囲に絞り、世界全体のズーム5を取得しない。
通常ソースとは表示ズームを分け、二重に色を重ねない。両ソースで同じ取得・保存処理を共有する。
地図ズーム3.5以上の解像度や取得レベルは従来どおり。

## 実測条件（2026-11-20）

実ブラウザーでWebGL描画を行い、430×932と1280×720のビューポートで確認した。
スマートフォン相当は画面寸法の再現であり、実機のCPU・通信速度を再現するものではない。

通信量をブラウザーのHTTPキャッシュ利用と区別するため、開発専用の同一オリジン中継を通した。
中継は国土地理院の元URLへアクセスし、画像本文・Cache-Control・ETag・Last-Modified・Expires・ステータスをそのまま返す。
配信元にTiming-Allow-Originがないため、Performance Resource Timingの転送量だけで判断しない。
中継で実際に発生した上流要求と本文バイト数を記録した。通常の直接取得でも別途表示を確認する。
本番コードには計測用中継・UI・同意画面のテスト用代替は含めない。

ズーム8・回転0・傾斜0で以下の地点を往復した（経度、緯度）。

1. A（137.5, 36）
2. 近距離（138.6, 36）→ A
3. 東北（140.8, 38.8）→ 北海道（142.5, 43）→ 中国（132.5, 34.5）→ 九州（131, 32）→ 近畿（135.5, 35）→ 関東（140, 36.5）→ A

コールド条件は異なる計測URLと新規ページでHTTPキャッシュ・メモリーの持ち越しを避け、専用Cache Storageも消去した。
再読み込み条件は専用Cache Storageを保持し、ページとデコード済み画像を作り直した。

## 結果

### 広域移動後にAへ戻る

|画面|正常な画像の再取得（前→後）|本文転送量（前→後）|地形描画完了まで（前→後）|
|---|---:|---:|---:|
|430×932|4→0件|582,092→0 bytes|119.7→65.1ms|
|1280×720|7→0件|927,824→0 bytes|292.9→144.2ms|

PCには提供元の海域等の欠損タイル404が別途ある。復帰時は修正前後とも2件・621bytesであり、正常画像として数えていない。
404を透明画像などの正常応答に置き換えたり、取得失敗を永続保存することはしていない。
近距離の往復は両画面とも修正前から正常画像の再取得0件だった。

### コールドと再読み込み

- 430×932のコールド取得は前後とも24画像・3,259,876bytes。今回の施策は未取得画像の転送量を削らない。
- PCのコールド取得は正常画像約5.8MB。表示範囲更新中の中止・遅れて完了した要求があり、初回の件数・時間を速度改善の根拠には使わない。
- 改善後の再読み込みで正常画像の上流取得は両画面とも0件。スマートフォン相当は描画まで392.0ms、PCは972.3msだった。
- PCの保存件数上限256件では、広域移動で容量上限より先に件数上限へ達し、正常画像3件を再取得した。32MiBの容量制限は保ち、件数上限を512件にして再確認した。

### 残る処理

通信とデコード・描画を分けて計測した。復帰時の画像デコードはスマートフォン相当6回、PC6回であり、画像をGPUキャッシュから追い出した後のデコードは残る。
その所要時間の合計は71.2ms / 163.0msだったが、並列実行を含むため壁時計時間や純粋なCPU時間ではない。
描画完了までの時間は、移動開始から対象地形ソースの準備と次フレームまでの壁時計時間であり、純粋なGPU描画時間ではない。
単一環境での計測値で、通信状態・描画負荷によって変動する。初回表示や全端末で一定割合高速化するという保証はしない。

保存期限切れ・容量超過・ブラウザーによるストレージ削除時は再取得する。保存だけでオフライン動作を保証するものではない。

## 移動・拡大縮小中の補完（2026-11-20）

傾けた地図でタイルが大きく欠ける問題について、次の2点を修正した。

1. 専用プロトコルがHTTP 404を通常のErrorに変換し、`status` を失っていた。MapLibre 5.24のTileManagerは404を契機に親タイルを取得するため、`status` と元URLを保持して例外を返すようにした。429・503等も元のステータスを保持する。失敗を成功画像として保存する処理は追加していない。
2. 既定の `cancelPendingTileRequestsWhileZooming: true` は、拡大中にまだ読み込み中の粗いタイルを中止する。これを `false` にし、現在の表示を補う親タイルが届くまで要求を保持する。表示範囲から外れたタイルまで保持する設定ではない。通信完了後は従来どおり詳細画像へ切り替わる。

これにより、一度要求した粗いタイルを中断して再び空白に戻す動作を抑える。
保存容量・期限・PNGの解像度・配色は変更しない。全国の全ズームを一括ダウンロードする方式ではなく、必要になった範囲を読み込み・保存する。

実ブラウザーのMapLibreで以下を確認した。

- **404の再現**：傾斜60°、ズーム6、詳細ズーム7の応答だけ404にし、それより粗いタイルには実際の国土地理院画像を返した。修正前はズーム7の43要求が失敗して親要求が発生せず、画像描画は0。修正後はズーム6を17件・ズーム5を2件取得し、地形が補完された。既存のHTTPキャッシュを専用キャッシュと誤認しないよう、専用メモリー／Cache Storageはこの試験では使用していない。
- **遅延・ズームの再現**：国土地理院から取得した1枚のPNGを試験用タイル応答として使用し、通信速度を固定する合成テストを行った。粗いタイルを500ms、詳細を2,500ms遅らせ、粗いタイルの取得開始120ms後にズーム4→6へ移動した。傾斜60°、移動後1,200msの時点で、修正前は16件の粗い要求を中止し、描画画像はなかった。修正後は範囲外の9件のみを中止し、粗い画像が画面を覆った。詳細到着後は両条件とも要求59件で正常に完了した。PNG固定応答の試験は読み込み制御の検証であり、地理的な形状の正確さを検証するものではない。
- `TerrainTileCacheTests.mjs` では、404・429・503のステータス保持と、失敗したタイルが保存されないことを確認した。

未取得の範囲には通信待ちが必要で、配信元に画像がない地域を生成して埋めるものではない。
